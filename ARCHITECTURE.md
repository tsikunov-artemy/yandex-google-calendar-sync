# Calendar sync code walkthrough

The default mode mirrors one Yandex calendar into Google. Users manage work meetings and invitations in the source calendar. Integrations read the Google copy. The two places to start are `SyncEngine.run_sync` for changes to whole events and `GoogleMirror.sync` for individual occurrences of a series. [Engine dispatch](src/sync/engine.py#L102) · [Occurrence dispatch](src/sync/mirror.py#L125)

## Follow a moved meeting

Suppose a weekly meeting moves from Monday at 11:00 to Tuesday at 15:00. Other Mondays stay at 11:00. The following steps trace the values used to find and update the Monday occurrence and keep its **existing Google event ID**.

| Step | Decision in the code | Jump to source |
|---|---|---|
| Read the series | `run_sync` calls `YandexProvider.get_events` with the configured date window (default −30/+180 days). The CalDAV search uses `expand=False`. `read_components` walks every `VEVENT` in each resource, including the master and its exceptions. | [Caller](src/sync/engine.py#L59) · [CalDAV read](src/providers/yandex.py#L77) · [Parser test](tests/test_mirror.py#L25) |
| Keep both times | `_parse_component` reads `RECURRENCE-ID` as the original Monday and `DTSTART` as Tuesday. Both dates share the series UID. For a cancellation without a start, the parser falls back to the original date. | [Time fields](src/providers/yandex.py#L169) · [Resulting model](src/providers/yandex.py#L266) · [Cancellation test](tests/test_mirror.py#L54) |
| Route the exception | `detect_yandex_changes` counts every UID as present, then skips exceptions when comparing masters. This protects a series when the query returns only an exception. `GoogleMirror.sync` separately indexes exceptions by `(uid, original time)`. | [Master comparison](src/sync/differ.py#L22) · [Exception index](src/sync/mirror.py#L134) · [Exception-only test](tests/test_mirror.py#L74) |
| Locate Monday in Google | `event_map` supplies the Google ID of the **series**. During an audit the mirror first checks a lookup table indexed by Google's `recurringEventId` and `originalStartTime`. On a miss, `lookup` calls `events.instances(originalStart=…)` and checks the returned original time. Multiple matches raise an error. | [Index](src/sync/mirror.py#L66) · [Lookup call site](src/sync/mirror.py#L160) · [Match check](src/sync/mirror.py#L92) |
| Write Tuesday | `difference` compares the desired fields with that occurrence. `patch_item` sends changed fields to its existing `item["id"]`, with the Google ETag in `If-Match`. A cancellation patches the status. Identical fields produce no write. | [Comparison](src/sync/mirror.py#L29) · [Conditional patch](src/sync/mirror.py#L120) · [Test of ID reuse and repeat cycles](tests/test_mirror.py#L81) |

## Create, edit or delete a whole event

| Source change | Google operation and local state | Jump to source |
|---|---|---|
| New UID | The differ emits `NEW`. `GoogleProvider.create_event` imports the event with its iCalendar UID. After the API returns, the engine commits the returned Google ID and source content hash to `event_map`. Import and SQLite commit are separate operations. | [Change detection](src/sync/differ.py#L29) · [Import and UID fallback](src/providers/google.py#L214) · [Save mapping](src/sync/engine.py#L188) |
| Known UID, changed fields | `content_hash` includes times, status, recurrence rules, exceptions expressed as excluded dates, attendees and reminders. A hash mismatch selects `MODIFIED`. The engine updates the mapped Google event, then records the new hash and ETag. | [Hashed fields](src/models/event.py#L63) · [Update branch](src/sync/engine.py#L206) · [Google API request](src/providers/google.py#L270) |
| UID disappears from the window | The differ proposes `DELETED`. `confirmed_absent` checks the stored CalDAV resource when available, then searches by UID if needed. Only confirmed absence reaches the Google deletion and subsequent mapping removal. A timeout leaves the mapping in place. | [Confirmation](src/providers/yandex.py#L89) · [Delete branch](src/sync/engine.py#L236) · [Timeout and missing-UID test](tests/test_mirror.py#L63) |

**Changing a copied field.** For example, `CONFERENCE` and `X-TELEMOST-CONFERENCE` URLs become part of the description. Trace a field through the parser, model hash, Google request body and audit comparison. These lists serve different purposes. Attendees and reminders contribute to source change detection, while the audit compares title, description, location, status, start and end. The Google serializer currently assigns imported attendees the response status `accepted`. The mirror therefore cannot serve as a record of actual RSVPs. [Read conference links](src/providers/yandex.py#L254) · [Hash](src/models/event.py#L63) · [Serialize to Google](src/providers/google.py#L416) · [Audit field list](src/sync/mirror.py#L33)

## Polling, audit and recovery

- **Calendar selection.** `SyncEngine.connect` connects Yandex first and Google second. Yandex selects the named calendar or the first available one. Google loads OAuth credentials, uses the configured calendar ID and, when a name is set, finds or creates that calendar and uses its ID. [Connection order](src/sync/engine.py#L35) · [Yandex selection](src/providers/yandex.py#L40) · [Google selection](src/providers/google.py#L37) · [OAuth setup](scripts/setup_google_oauth.py#L28)
- **Startup and cadence.** `main` loads settings, constructs the engine, opens SQLite and connects both providers. `--once` runs one cycle. The daemon sleeps *after* each cycle. Weekday working hours default to 05:00–18:00 UTC, with a 60-second pause inside that window and 300 seconds outside it. To change the cadence, follow the delay passed to the sleep loop. [Defaults](src/config.py#L43) · [Engine wiring](src/sync/engine.py#L26) · [Daemon loop](src/main.py#L73) · [Scheduler constants](src/sync/scheduler.py#L26)
- **Two-week audit.** On startup and on the first cycle due after ten minutes, the mirror reads expanded Yandex occurrences and paginated Google instances for 14 calendar days starting at Moscow midnight. Explicit exceptions can also be processed between audits throughout the wider sync window. The audit deadline and checked exception hashes live in process memory. [Window and exception selection](src/sync/mirror.py#L136) · [Pagination](src/sync/mirror.py#L60) · [Advance the deadline](src/sync/mirror.py#L187)
- **Missing or stale copy.** If an expected active occurrence cannot be found, the mirror tries to repair its master, then repeats the lookup. Reimporting a missing master can produce a new Google ID, which replaces the old mapping. An unmatched managed Google occurrence increments `extra` and flags the audit for review. [Repair and second lookup](src/sync/mirror.py#L164) · [Save replacement ID](src/sync/mirror.py#L115) · [Extra occurrences](src/sync/mirror.py#L182)
- **Failed write.** An exception-level failure emits `mirror.repair_failed` with the UID and original time. The hash is recorded only after successful processing. A failed audit remains due. `run_sync` records per-event errors as `partial` and a cycle-level exception as `error` in `sync_log`. Inspect `docker compose logs --tail=200 calendar-sync` and the corresponding SQLite row. [Failure branch](src/sync/mirror.py#L177) · [Cycle outcome](src/sync/engine.py#L151) · [SQLite schema](src/db/engine.py#L37) · [Retry test](tests/test_mirror.py#L111)

## Experimental reverse sync

`google_to_yandex` and `bidirectional` activate another path. `_get_google_events` loads the cursor from `sync_state`, fetches changes and saves the next token **before** the engine applies them to Yandex. A later write failure can therefore leave a change behind the saved cursor. Only `yandex_to_google` runs the occurrence mirror above. [Cursor ordering](src/sync/engine.py#L164) · [Write dispatch](src/sync/engine.py#L113) · [Mirror mode guard](src/sync/engine.py#L124)

`detect_google_changes` proposes deletion only for a mapped cancellation. A Google item without a start can be discarded by the parser before the differ sees it. In bidirectional mode, concurrent modifications are matched by UID and resolved by the configured strategy. The Yandex writer serializes a fresh `VEVENT` on update. Its serializer omits organizer and attendee fields, so this path cannot preserve a guest list or implement sending invitations from Yandex. [Google parser](src/providers/google.py#L334) · [Delta test](tests/test_google_changes.py#L9) · [Conflict matching](src/sync/conflict.py#L11) · [Resolution](src/sync/conflict.py#L42) · [CalDAV replacement](src/providers/yandex.py#L138) · [Serialized fields](src/providers/yandex.py#L285)

Run `uv run --locked pytest -q` to exercise the linked scenarios. The ID-reuse test supplies a Google instance and captures the patch in memory. It checks the chosen ID, duplicate writes and repair of a changed description. The suite has no end-to-end test for OAuth, initial master import, Google instance lookup, or invitation delivery.
